# AI Passport —— 给豆包输入法用的无线麦克风

隔着房间对豆包输入法说话，不需要联网。按一下卡片上的键、说话，文字就出现在光标处。

```
  卡片                          Mac
  ┌──────────┐   BLE GATT   ┌─────────────┐
  │ 麦克风   │ 16 kHz μ-law │ recv-ble    │
  │ 三个按键 ├─────────────►│ agent       │──► 虚拟麦克风 ──► 豆包 ──► 出字
  │ 屏幕     │  每帧 480    │             │
  └──────────┘  个采样      └─────────────┘
```

## 好用在哪

- **链路里没有网络。** 只有到笔记本的蓝牙 LE。没 Wi-Fi 的会议室照样用。
- **你停它就停。** 静音 3 秒自动结束本次录音。
- **一键发送。** 录音中按确定：停止、等豆包修订完句子、然后回车。
- **屏幕会告诉你它在工作。** 杯子上方的星星随声音长大，活着的链路不会看起来像死的。
- **没事的时候屏幕全暗。** 空闲 20 秒背光直接关到 0，任意按键或重连立刻回来。背光是
  520 mAh 电池上最大的一笔开销，而它此前是全天全亮的。
- **登录即启、自己恢复。** 卡片休眠或走远后 agent 自动重连，进程崩了 launchd 拉起来。

## 按键

| 按键 | 动作 |
| --- | --- |
| 下 | 开始 / 停止录音（按下即触发，不等抬手）|
| 确定 | 停止并发送（按下即发，不等抬手）|
| 上 | 删除上一句 |
| 上，按住 1 秒 | 持续删除，松手即停 |
| 确定，按住 2.5 秒 | 离开语音模式，进入 Wi-Fi / 飞书配置 |

按键在接触瞬间就生效，不等抬手。等「单击」意味着既要等手指离开、又要等约 180 ms 的
双击判别窗口过期，那是整条输入路径里最长的一段延迟，也正是让人觉得「按键很慢」的
那一段。这两个动作都可以补救 —— 再按一次、再说一遍 —— 所以等着看会不会有第二次点击
毫无收益。两个长按阈值不同，是因为等待的感受不同：删除是直接操纵，必须快；离开屏幕
会打断录音，就该难触发。

## 安装

```sh
brew install blackhole-2ch python@3.11        # bleak 需要 Python 3.10+
python3.11 -m pip install bleak sounddevice numpy pyautogui pyobjc-framework-Cocoa

. $IDF_PATH/export.sh                          # ESP-IDF v5.5.3
idf.py -p /dev/cu.usbmodemXXXX flash

tools/install-mic-agent.sh                     # launchd agent，登录即启
```

先装依赖再跑脚本：脚本自己不装任何东西，只是去找一个已经装好的解释器。而且它只检查
`bleak`、`sounddevice`、`numpy` 三个 —— 漏掉 `pyautogui` 的话，agent 会欢快地推流，
但一个字都不会打出来。

然后是三个容易漏掉的设置：

1. **系统设置 → 隐私与安全性 → 辅助功能 和 蓝牙**：把 agent 用的那个 Python 加进去。
   没有辅助功能权限，macOS 会静默丢弃合成按键，于是什么都转不出来。
2. **音频 MIDI 设置 → + → 创建聚合设备**，勾选 **BlackHole 2ch**，起个名字，然后在
   豆包里把麦克风选成*它*。豆包会拒绝 Core Audio 传输类型为 `Virtual` 的设备，而
   BlackHole 报告的正是 `Virtual`；聚合设备报告 `Unknown`，能通过。
   **BlackHole 自己永远不会出现在豆包的列表里 —— 整件事的关键就在这一步。**
3. **豆包的语音快捷键必须设为右 Option**，因为 agent 在每次录音期间一直按住这个键。

验证：按下键，出声数到三。星星应该变大，文字应该出现。
`tail -f /tmp/aipassport-mic.log` 能看到 agent 在做什么，
[设计文档](docs/software-design/)里写了那些「看起来像成功」的故障 ——
头号是豆包悄悄在听内置麦克风。

## 原理

**用 μ-law,不用有状态编码。** ADPCM 是有状态的,丢一个通知就污染之后的全部音频。
G.711 μ-law 逐样本独立,丢一帧只损失那一帧 —— 保住了裸 PCM 的这个性质,而字节数减半。

**链路限制的是每秒几个包,不是每秒几个字节。** BLE 每个连接事件大约只放行一个通知,
而 macOS 把连接间隔钉死在 30 ms 且拒绝协商(固件请求 15 ms,被 rc=554 拒绝),
上限约 34 个通知/秒。240 采样的 PCM 帧是 15 ms 音频,需要 66.7 个/秒 —— 缺口正好
一半,实测送达率 47-56%。而且它不以错误的形式出现:发不出去的通知堆在 NimBLE 的
mbuf 池里,池满后分配返回 NULL,设备**在空口之前就自己把帧丢了**。

所以一帧改成 480 个 μ-law 采样:30 ms、上线 482 字节 —— 和原来逐字节一样大的包 ——
每秒 33.3 个。实测 101-105% 的实时率,零丢帧,pool_dry 为 0。

带宽从来不是约束。当初选裸 PCM 的理由是「256 kbps 塞得进 BLE 的 ~700 kbps」,这话
没错,但回答的是错的问题。也不要反过来把 MTU 填得更满:252 采样(506/507 可用字节)
实测**更差**,89% → 69%,因为更满的包占用更多控制器 ACL 缓冲。两个方向上,留余量都
胜过占满。

**每帧带一个序号。** BLE 通知不会重传，没有序号的话，「丢了一帧」和「设备只是跑得慢」
无法区分。这个含混把排查引向错误的层三次；加上计数器后一个会话就定了案 ——
丢失发生在固件内部，不在空口。

**用背压，不用队列。** 采集 worker 只留一个重试位，不做缓冲。曾试过 4 帧队列又撤掉了：
它只能按链路的速度排空，而采集一直在填，结果 92% 的循环迭代发现队列满、什么都没发出去。

**输出流永不关闭。** 流式识别器容忍延迟但不容忍空洞。塞静音会让它的语音活动检测把
句子切成两半，而在两句之间关闭音频流，看起来就像麦克风被拔掉 —— 所以流只打开一次，
用 160 ms 预缓冲吸收 BLE 抖动。

这个预缓冲一点都不宽裕，而它是最容易被新来的人当成浪费的那个值。因为队列只按整帧
移动，实际有效深度是 180 ms；实测最低水位曾被抽到只剩 30 ms，而同一会话最坏帧到达
间隔是 178 ms —— 缓冲垫一直在满负荷工作。两次削减尝试（90 ms、100 ms）都丢了首字，
而当时每个计数器都读正常。
[`docs/software-design/voice-link-baseline.zh_CN.md`](docs/software-design/voice-link-baseline.zh_CN.md)
记录了这些实测，**在调整这条链路上任何延迟或缓冲参数之前先读它。**

**控制码的优先级高于音频。** 它们和每 30 ms 取一块的音频流共用 BLE 的 mbuf 池。
丢一帧音频是 30 ms 的声音；丢一个 STOP 会让豆包永远录下去。所以控制码会重试，
而且只在真正发出后才清除。按住删除同理只发两个边界 —— 重复由电脑端跑，按住两秒
只占链路两个通知而不是八十个 —— 而电脑端带一个 10 秒的死人开关，防的正是「结束
那个边界恰好丢了」。

**每种失败都有计数器，而且账必须对上。** mbuf 池干涸有两个捕获点 —— 2 字节包头拿不到
块，或者包头拿到了但 480 字节负载拿不到剩下的 —— 而有一段时间只上报了前者，于是把池
干涸低报了最多 4 倍，让一次真实退化读起来像「设备好像有点慢」。现在会话行两个都打，
另加 `unacct`：尝试数减掉所有已上报结果，必须为 0。任何其他值都意味着存在无人计数的
失败路径。`msys_min` 报告空闲 mbuf 最低水位，健康录音里读 72/72 —— 链路跟得上时，
池根本没被动过。

读这些数字有一个坑：`tried` 数的是通知**尝试次数**，不是帧数。被拒的帧会重试一次，
所以给 `tried` 加两次，`tried − sent = 2 × lost` 精确成立。真实丢帧率读主机侧的
`lost=`，永远不要读 `sent/tried`。

**信号在设备上做过处理。** 输入增益是 24 dB 而不是 30 —— 30 dB 下正常说话就会削顶，
而削顶是不可恢复的失真，识别器对它退化很快。一个单极 90 Hz 高通滤掉手持噪声和体传
震动，那些占了 11% 的能量，而 300-3400 Hz 的语音带只占 36%。把这个转折点挪到 150 Hz
试过并已回退：改完之后 300 Hz 以下能量实测**更高**，与理论矛盾，所以不论怎么解释，
这个改动都不成立。

**电平表也要算进帧预算。** RMS 每隔一帧跑一次、每八个采样取一个，因为它夹在采集读取
和 BLE 发送之间，跑在同一个核上。每个采样都算的话，实测送达率从 99% 掉到 95% ——
这个细节只有在测链路而不是测电平表时才会暴露。

## 还没解决的问题

约 7% 的录音有丢帧，以「自己来、自己走」的方式成片出现。机制是清楚的：每秒送达通知数
从约 33.6 掉到约 29，而设备固定生产 33.3，赤字积压进 mbuf 池直到分配失败。触发原因
不清楚 —— 连接间隔能回答它，而它还没进日志。已测到 5 次这样的事件，每次都自行恢复，
最差单次 35.6%。

计数器和推理过程在
[`docs/software-design/voice-link-baseline.zh_CN.md`](docs/software-design/voice-link-baseline.zh_CN.md)，
包括那些被推翻的假设。除了这条链路本身，它还有一个更普适的价值：其中几次走错路都源于
「在正常和异常下读数相同」的仪器，那比没有仪器更糟。

## 卡片上还有什么

长按确定键后面是一个飞书消息器，有自己的 Wi-Fi 和扫码配置。它早于麦克风存在，需要
你自己的飞书应用凭据，对语音输入不是必需的。见
[`docs/software-design/feishu-messenger.zh_CN.md`](docs/software-design/feishu-messenger.zh_CN.md)。
