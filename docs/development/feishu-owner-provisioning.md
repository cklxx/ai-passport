# Owner-provisioned Feishu application

This advanced mode lets each device owner use their own Feishu developer application. The generic firmware, website assets, release artifacts, and source tree contain no publisher App ID, App Secret, access token, or refresh token. The recommended one-time setup uses the device's temporary protected Wi-Fi portal from a phone; USB remains a fallback. The device then calls Feishu directly over Wi-Fi and no computer needs to remain online.

## 1. Resulting trust model

```text
Phone-local setup page (recommended) or USB provisioning tool (fallback)
  └─ random-password temporary AP / physical USB
      └─ owner App ID and App Secret in device NVS
          └─ Feishu device-authorization QR
              └─ owner access and refresh tokens in device NVS
                  └─ direct device-to-Feishu operation over Wi-Fi
```

The `lark-cli` executable is not copied to the device. An advanced user may configure the same application in `lark-cli`, but the device receives only that application's ID and secret. The device obtains its own token pair from the QR authorization shown on its screen.

## 2. Create the owner's Feishu application

Create a Feishu developer application owned by the person or organization that will own the device. Configure the application's availability so the intended account can use it, enable device authorization, and enable the minimum scopes required by the firmware:

```text
im:chat:readonly
im:message
im:message.p2p_msg:get_as_user
im:message.group_msg:get_as_user
speech_to_text:speech
offline_access
```

Conversation reads use the authorized user's token. Sends and replies use the application's tenant token and therefore appear as the application bot; the bot must be allowed in the target chat.

The application's security configuration must also allow refresh tokens. This switch is separate from the `offline_access` scope; without it Feishu accepts the QR authorization but returns only a short-lived access token, so the device intentionally rejects the incomplete binding.

The application permission and the user's OAuth grant are separate requirements. Enabling a scope in the developer console does not grant user access by itself. Enterprise policy may also require an administrator to publish or approve the application.

If the same application is also used with `lark-cli`, initialize a named profile without exposing the secret in the process list:

```bash
printf '%s' "$FEISHU_OWNER_APP_SECRET" | \
  lark-cli config init \
    --name ai-passport-owner \
    --app-id cli_example \
    --app-secret-stdin \
    --brand feishu
```

Do not put a real secret in shell history, documentation, issue reports, firmware configuration, or a source-controlled environment file.

## 3. Web one-click flow

The website keeps the existing Web Serial firmware installation. Its introduction must first tell users to create their enterprise custom app, enable the listed scopes, publish it, include themselves in its availability range, and copy App ID/App Secret from Credentials & Basic Information.

1. Flash the generic full firmware image.
2. Scan the device's first-run QR with a phone and configure the home 2.4 GHz Wi-Fi on its local page.
3. Scan the next device QR and enter the owner's App ID and App Secret. Values go directly through the local AP to the device, not to the publisher's server.
4. A device that already has Wi-Fi but lacks an owner app displays a `FoloFeishu-xxxx` Wi-Fi QR carrying a random WPA2 password.
5. After save, the temporary AP shuts down, home Wi-Fi resumes, and the device displays the Feishu authorization QR generated by that owner's app.
6. After approval, the device stores its own user tokens and opens the conversation list. The browser and computer are no longer required.

The embeddable USB fallback page is `tools/feishu-provision-web/index.html`. Production hosting must use HTTPS because browsers expose Web Serial only in a secure context. The production page must not add analytics, error reporting, persistence, or network submission for the credential fields.

## 4. Local command-line alternative

Install `pyserial`, connect the device over USB, and keep it on the private-application setup screen:

```bash
python3 -m pip install pyserial
python3 tools/feishu_provision.py \
  --port /dev/cu.usbmodemXXXX \
  --app-id cli_example
```

The tool prompts for App Secret with hidden input. It never accepts the secret as a command-line flag. If exactly one USB serial port is visible, `--port` may be omitted.

## 5. Serial protocol

The common website/CLI protocol is one bounded UTF-8 line:

```text
FAP-FEISHU/1 <base64(JSON)>\n
```

The decoded JSON contains only:

```json
{"app_id":"cli_example","app_secret":"redacted"}
```

The device replies with `FAP-FEISHU/1 OK` or `FAP-FEISHU/1 ERROR`. It accepts the protocol only while onboarding has no valid application configuration. Base64 is framing, not encryption; confidentiality relies on the physical USB link and the trusted local browser or tool. Never expose this provisioning receiver over Wi-Fi or BLE without adding an authenticated encrypted session.

Writing another application clears the previous access and refresh tokens before the new QR flow begins. The host never supplies user tokens, which avoids copying or exporting `lark-cli`'s private token store.

Owner-provisioned records carry a storage-version marker. After upgrading from firmware that predated this flow, unmarked Feishu credentials are rejected and the owner must provision their own application once; Wi-Fi configuration is unaffected.

## 6. Storage and production hardening

Development builds prove the workflow but do not make extracted Flash confidential. Before production distribution:

- enable Secure Boot, Flash Encryption, and NVS Encryption;
- prevent serial boot logs and crash dumps from printing credentials or tokens;
- accept owner provisioning only from an explicit physical maintenance/onboarding state;
- clear input buffers immediately after use;
- make unbind erase App ID, App Secret, access token, refresh token, and cached conversation state;
- document that rotating App Secret requires owner reprovisioning;
- treat a lost or physically compromised development device as a reason to revoke the Feishu grant and rotate that owner's App Secret.

The release gate must scan source, generated configuration, merged images, and packaged website files for known test or publisher identifiers. A successful generic build must work with empty application configuration and wait for owner provisioning instead of generating a publisher QR.

## 7. Recovery and troubleshooting

| Symptom | Meaning | Resolution |
| --- | --- | --- |
| Authorization page names another person's application | That person's App ID is still stored or built into the image | Unbind/erase credentials, flash a generic build, and provision the owner's app |
| User has no permission to use the application | Application availability or enterprise approval excludes that account | Update the owner's app availability and publish/approve it |
| Web Serial cannot open | Another tab, flasher, or serial monitor owns the port | Close the other transport and reconnect |
| Device reports `ERROR` | Invalid App ID/Secret shape or NVS write failure | Verify the `cli_` App ID and retry; inspect redacted device logs if needed |
| QR succeeds but the device reports that refresh tokens are disabled | The app security setting disallows refresh tokens, or `offline_access` is missing | Allow refresh tokens, enable `offline_access`, publish the app, then authorize with a new QR |
| App Secret was rotated | Stored secret can no longer refresh tokens | Re-enter owner provisioning and scan a new QR |

Unbinding on the device clears local state only. To revoke server-side access completely, the owner must also remove the application's authorization in Feishu.
