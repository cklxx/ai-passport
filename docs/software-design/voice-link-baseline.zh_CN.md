# BLE 语音链路基准

这份文档存在的唯一理由：**在调整这条链路上的任何延迟或缓冲参数之前先读它。**

2026-09-01 到 09-02 期间，这条链路被反复调整了二十多次，其中多次是在错误的
证据上做的错误改动，然后回退。下面是当时实测到的数字、被推翻的假设，以及为什么
某些看起来"明显浪费"的余量其实一点都不多。

## 当前基准（2026-09-02，零丢帧）

设备侧，`island: device read=` 一行：

| 字段 | 正常值 | 含义 |
| --- | --- | --- |
| `tried` / `sent` | **相等** | 通知**尝试**数 / 被 BLE 接受的尝试数 —— 见下，这不是帧数 |
| `pool_dry` + `pool_mid` | **0** | mbuf 池干涸：包头分配不到 / 负载 append 不进去 |
| `unacct` | **0** | `tried` 减掉所有已上报结果。非 0 说明存在无人计数的失败路径 |
| `msys_min` | 20-40 | 空闲 mbuf 最低水位。接近 0 说明池即将开始拒帧 |
| `refused` | 0 | 主机栈拒绝已排队通知的次数 |
| `i2s_ovf` | 0-1 | I2S 采集环溢出（单位是 DMA 描述符，不是 BLE 帧）|

**`tried` 数的是尝试次数，不是帧数。** 被拒的帧会重试一次（`demo_voice.c` 的
backlog），于是它给 `tried` 加了两次。在整个退化窗口上实测，
`tried - sent = 2 × lost + rescued` 在全部 9 个会话中精确成立
（553 = 2×275 + 3、390 = 2×195、240 = 2×120……）。所以 `sent / tried`
**把丢帧率又算了一遍**：最差那个会话按尝试算是 68.5%，按帧算是 81.4%，
而 81.4% 正是主机侧 `lost=` 独立报出的数。**真实送达率读 `lost=`**，
永远不要读 `sent/tried`。唯一采集帧数 = `in/480 + lost`。

主机侧，`island: session end` 一行：

| 字段 | 正常值 | 含义 |
| --- | --- | --- |
| 实时率 | **101-107%** | 收到的采样数 / 会话时长 |
| `lost` | **0f in 0 gaps** | 按序号推断的链路丢失 |
| `underrun` | **0** | 会话期间的饥饿。非 0 就是缺陷 |
| `tail` | 7-12 | STOP 之后队列排空的回调数，属正常 |
| `lowater` | **30-180ms** | 会话期间队列最浅深度 |
| `gapmax` | 89-178ms | 最坏帧到达间隔 |
| `stop->release` | **488-503ms** | 松手到放开推话键，方差仅 15ms |
| `rx1->audible` | 47-103ms | 首帧到出声 |

## 唯一在真实使用中见到过的失效模式

2026-09-02 有连续 9 个会话退化到送达 81-95%，然后自己恢复了。记在这里是因为
**没有任何代码改动导致它，也没有任何代码改动结束它** —— 恢复发生在两个连续会话
之间，中间没有重启、没有重连、没有烧录，也就是说同一个二进制既产出 81% 也产出
100%。

日志能确立的部分：

| 量 | 退化（7 个 >10s 会话） | 正常（35 个 >10s 会话） |
| --- | --- | --- |
| 每秒送达的通知数 | 26.9-31.6，中位数 **29.1** | 33.3-33.9，中位数 **33.6** |
| `lowater` | 每个会话都是 0 ms | 30-180 ms |

两个区间完全不重叠。设备按 33.3 帧/秒生产且无法变慢；当空口只承载 29/秒时，
那 4/秒的赤字（13%，与实测 7-19% 丢帧吻合）就积压进 msys 池直到分配失败，
于是**设备在空口之前自己把帧丢了**。全程 `refused=0`、`rc=0`：射频从未拒绝任何
东西，空口上一帧都没丢。

所以问题不是「池为什么会干」—— 那是结果。问题是
**「链路为什么每秒只送 29 条通知而不是 33 条」**。连接间隔能回答它，而它不在任何
日志里；`msys_min`（2026-09-02 新增）现在能显示一个健康会话离同一道悬崖有多近。

这个窗口给出两条仪器教训，都属于下面第 3 条规矩：

- **单看 `pool_dry` 把池干涸低报了约 4 倍。** 池干涸有两个捕获点，只上报了一个。
  见上面 `tried`/`sent` 那一节。
- **`read_us / 时长` 无法测量 worker 的 CPU 余量。** 它在健康和退化会话里都读约
  96%，因为 `bsp_audio_read` 阻塞等 I2S DMA，是所有空闲时间的汇 —— 代数上两边都
  约等于 `1 − send/时长`。对这个问题它是个死仪器。要用唯一帧率（≈33/秒）配合
  `i2s_ovf=0`，那个才真正区分「采集跟上了」和「采集掉队了」。
## 三条硬约束

**BLE 限制的是每秒通知条数，不是带宽。** macOS 把连接间隔钉死在 30 ms 且拒绝协商
（固件请求 15 ms 被 rc=554 拒绝），一个连接事件大约放行一个通知，上限约 34 条/秒。
这是整条链路的根约束，改不了。

**帧长必须落在这个上限之内。** 480 个 μ-law 采样 = 30 ms 音频 = 482 字节 = 33.3 条/秒。
曾经的 240 采样 16-bit PCM 同样是 482 字节，但需要 66.7 条/秒 —— 缺口正好一半，实测
送达率 47-56%。而且它不以错误形式出现：发不出的通知堆满 NimBLE 的 mbuf 池，分配返回
NULL，**设备在空口之前自己把帧丢了**，主机侧只看到"设备好像跑得慢"。

**真正的上限是分片数，不是 MTU。** 值 V 占用 V + 3 (ATT) + 4 (L2CAP) 字节，按 251 字节
的链路层 PDU 分片，而射频每个连接事件放行的是固定数量的**分片**。252 采样那次实验
（506 字节）通知数只降 4.8%，分片数却涨 43%，送达率从 89% 掉到 69%。单参数分片模型
预测 70%，实测 69%。所以 `voice_ble.c` 的越界检查按 `V + 7 <= 502` 判，不按 MTU
——MTU 会放行到 509，正好落在会复现那次退化的区间里。

## 不要动这些，以及为什么

**预缓冲（`prebuf`，`island_agent.py`）。** 名义 160 ms，实际有效深度 **180 ms** ——
队列只按整帧移动，`int(0.16 * 16000) = 2560` 采样要到第 6 帧 2880 才越过阈值。
实测 `lowater` 在 30-180 ms 之间横跨整个深度，最坏那次只剩 30 ms，而同一会话
`gapmax` 是 178 ms。**这个缓冲垫在满负荷工作，余量本来就是勉强的。**

历史上两次降低都失败：90 ms「明显破坏了豆包的增量输出」，100 ms「每个计数器都正常
却丢了首字」。2026-09-01 又一次砍到 90 ms，首字再次丢失，已回退。

**帧长。** 不要为了填满 MTU 加大（见上面的分片约束），也不要为降延迟减小 —— 10 ms
帧曾让链路结构性饿死，只送达 68%。

**I2S 环深度（`bsp_audio.c`，`dma_desc_num = 10`）。** 提到 20 曾让设备直接不工作
（按键事件完全到不了分发器），因为这些缓冲来自内部 RAM，翻三倍会饿死初始化路径。

## 被推翻的假设

记录这些不是为了自责，是因为**同样的错误证据还摆在那里，下一个人会重新捡起来**。

**「`lowater` 一直是 0，说明缓冲垫从没被用过」—— 仪器是坏的。** 采样点原先无条件执行，
而 STOP 之后队列排空的若干次回调都在会话结束打印之前，于是 `lowater` 在**任何**情况下
都读 0：零丢帧的会话读 0，丢帧 16% 的会话也读 0。一个在两种极端下读数相同的指标什么
也没测量。修好后真相相反：缓冲垫一直在被消耗到只剩 30-120 ms。

**「`underrun` 只有 8 次，很健康」—— 数错了对象。** 那 8 次全是 STOP 之后的排空，不是
饥饿。拆成会话内 `underrun` 和尾部 `tail` 之后，会话内真实饥饿是 **0**。

**「带宽够，256 kbps 远小于 BLE 的 700 kbps」—— 算式没错，问的问题错了。** 该问每秒
几个包。这个误判让 μ-law 这条正解被搁置了整整一天。

**「是那次重连导致的」—— 73 组重连前后配对，中位数差 0.0pp。** 重连无害。

**「主机负载/磁盘满是主因」—— `pearson(load, 送达%) = +0.111`，符号都是反的。** 全日志
最差的一轮跑在最低负载上，最好的一轮跑在近两倍负载上。

**「252 采样失败证明包不能太满」—— 它证明的是分片不能变多。** 同一份数据，之前的解释
是错的。

## 改这条链路的规矩

1. **一次只改一个参数**，并且留下对照。同时改三个数字然后凭体感判断，等于没测。
2. **计数器全绿不等于没问题。** 这个文件里有明确记录：100 ms 预缓冲「每个计数器都
   正常却丢了首字」。听感回归无法被计数器反驳。
3. **改之前先确认仪器是活的。** 一个在正常和异常下读数相同的指标，是负资产。
4. **`stop->release` 里的 330 ms 是豆包的修订窗口**，其依据（250 ms 丢最后一个字，
   330 ms 不丢）是在丢帧 12-50% 时测的。当时补的可能是**丢帧**而不是修订时间。
   现在零丢帧，理论上可重测 —— 但要按第 1 条来。

## 尾部 490 ms 的构成

实测 488-503 ms，方差仅 15 ms，说明是确定性等待。构成（`island_agent.py` 的 `drain()`）：

| 段 | 实测 | 说明 |
| --- | --- | --- |
| 排空循环 `range(10)` | **117 ms** | **从不提前退出** —— STOP 时队列里有 124-274 ms 音频，100 ms 排不完 |
| 播出余量 `sleep(0.03)` | 34 ms | 按听感调出的下限，不是算出来的（`744372b` 用 0.05 修了可听的截断，`c61ae9f` 降到 0.03 并经听感确认）|
| 豆包修订窗口 `sleep(0.33)` | 333 ms | 唯一大头，见上面第 4 条 |

**闸门在这两段里全程开着**，是 `f27f08b` 故意改的：关闸会让豆包对着静音修订。

那它听到什么？队列此时已干，`cb()` 走修复分支约 11 次 —— 而 `tail[0]` 只在消费路径
（那个分支 `return` 之下）赋值，所以 11 次回调**发出的是同一个 30 ms 块的镜像**。
相同内容平铺意味着每 30 ms 一道接缝（实测约 6800 LSB，块内最大步进约 2900），
即一列 33 Hz 的咔哒声，带着最后一个真实音素的频谱，持续整个修订窗口。
会话中途不会出现，因为那里最多干涸一次。

**故意不动它。** 三路独立审查都认为修法不明显 —— 淡出静音、推进镜像、改发噪声
三种方案都被逐一论证并否掉了 —— 而这段修复代码与会话内路径共用，动它就动到了
当前零丢帧构建的地基。真要改，用 `stats["t1"]` 把尾部和会话内分开，并按第 1 条
听感验证。

## NFC 说明

NTAG213 是**被动标签，MCU 侧没有任何 API**，固件里不存在也不可能存在 NFC 代码。
它无法用于「碰一下连 Wi-Fi」：SoftAP 密码由 `setup_portal.c` 每次随机生成、只嵌在屏幕
二维码里，而 MCU 写不进标签，标签只能存出厂写死的内容。固定密码则等于没有密码。
（此外 iOS 不支持通过 NFC 标签加入 Wi-Fi。）标签唯一合理的用途是用手机写一条指向
配网页面的 URL，属于一次性配置，不是固件功能。
